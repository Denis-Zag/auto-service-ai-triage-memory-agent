# Auto Service AI Triage Memory Agent

Учебное развитие проекта Auto Service AI Triage. Сервис сохранил готовый
endpoint классификации обращений и получил диалогового LangChain-агента, который
по шагам собирает сведения о неисправности, помнит контекст конкретного диалога
и передаёт заполненную заявку в существующий триаж через собственный tool.

## Что добавлено

- `POST /agent/chat` для пошагового диалога с клиентом;
- кратковременная память LangGraph с постоянными checkpoint в SQLite;
- разделение памяти по сочетанию `client_id` и `thread_id`;
- собственный tool `submit_triage_request`;
- структурированный ответ агента через Pydantic;
- повторное использование существующей классификации и журнала заявок;
- офлайн-тесты API, структурированных схем, изоляции ID и собственного tool;
- немедленное завершение шага после успешного сохранения заявки без повторного
  вызова tool.

Исходный `POST /triage` сохранён и продолжает работать независимо от агента.

## Как работает система

```text
Сообщение клиента
        ↓
POST /agent/chat
        ↓
LangChain-агент ← SQLite checkpoint по client_id + thread_id
        ↓
Данных достаточно?
  ├─ нет → один уточняющий вопрос → сохранить состояние
  └─ да  → submit_triage_request
                    ↓
              существующий триаж
                    ↓
          SQLite или Turso: таблица tickets
                    ↓
       структурированный ответ с ticket_id
```

Модель не получает открытые `client_id` и `thread_id` в качестве содержимого
сообщения. Для checkpoint используется SHA-256 от их сочетания. Одинаковый
`thread_id` у разных клиентов создаёт разные ветки памяти.

## Стек

- Python 3.12;
- FastAPI и Pydantic;
- LangChain и LangGraph;
- `langchain-openai` для OpenAI-совместимого ProxyAPI;
- `langgraph-checkpoint-sqlite` для памяти диалога;
- SQLite или Turso для журнала заявок;
- pytest;
- Docker и Docker Compose.

## Контракт диалогового агента

### Запрос

```http
POST /agent/chat
Content-Type: application/json
```

```json
{
  "client_id": "client-001",
  "thread_id": "dialog-001",
  "message": "У меня Lada Vesta, сегодня появился стук при повороте.",
  "channel": "chat"
}
```

- `client_id` отделяет данные клиентов;
- `thread_id` обозначает отдельный разговор одного клиента;
- повторные сообщения того же разговора должны передавать прежние значения;
- новый `thread_id` начинает отдельный контекст.

### Ответ во время сбора данных

```json
{
  "message": "Уточните, пожалуйста, когда именно появился стук.",
  "status": "collecting",
  "missing_fields": ["время появления"],
  "ticket_id": null,
  "triage": null
}
```

### Ответ после сохранения заявки

```json
{
  "message": "Заявка сохранена под номером 17.",
  "status": "submitted",
  "missing_fields": [],
  "ticket_id": 17,
  "triage": {
    "category": "support",
    "draft_reply": "Передадим описание мастеру для первичной проверки.",
    "confidence": "high",
    "escalate": false
  }
}
```

При ошибке внешней модели API возвращает структурированный результат со
`status=error` и понятным предложением передать обращение оператору.

## Собственный tool

`submit_triage_request` принимает только сведения, которые агент должен получить
от клиента:

- автомобиль;
- описание проблемы;
- время и обстоятельства появления;
- дополнительные сведения, если они были сообщены.

`client_id`, канал, настройки базы и ключ API не доступны модели как параметры
tool. Они фиксируются приложением. Tool собирает обычный `TriageRequest`, вызывает
существующий сервис триажа и возвращает агенту номер сохранённой заявки и
структурированный результат.

## Память

История и промежуточное состояние диалога сохраняются в
`data/agent_memory.db`. Это не долговременный профиль клиента: память относится
только к одному `thread_id`.

Файл checkpoint не добавляется в Git. При локальном запуске и Docker Compose он
сохраняется между перезапусками. Для будущего публичного развёртывания необходимо
отдельно выбрать постоянное серверное хранилище; временная файловая система
бесплатного контейнера для этого не подходит.

Журнал готовых обращений сохраняется отдельно в `data/triage.db` или Turso.

## Исходный endpoint триажа

```http
POST /triage
Content-Type: application/json
```

```json
{
  "text": "После ремонта снова появился стук в подвеске.",
  "channel": "chat",
  "client_id": "client-001"
}
```

Ответ содержит категорию `billing`, `support`, `complaint` или `other`, черновик
ответа, уровень уверенности и признак передачи оператору.

## Настройка

Создайте локальный `.env` на основе `.env.example`:

```env
PROXYAPI_KEY=
PROXYAPI_BASE_URL=https://api.proxyapi.ru/v1
LLM_MODEL=gpt-4o-mini
LLM_TEMPERATURE=0.2
LLM_TIMEOUT_SECONDS=30
DATABASE_BACKEND=sqlite
DATABASE_PATH=data/triage.db
AGENT_MEMORY_PATH=data/agent_memory.db
TURSO_DATABASE_URL=
TURSO_AUTH_TOKEN=
REQUESTS_PER_MINUTE=10
USE_LLM=true
```

Секретный ключ хранится только в `.env`. Файл исключён из Git и Docker-контекста.

## Локальный запуск

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Swagger UI будет доступен по адресу `http://127.0.0.1:8000/docs`.

```powershell
docker compose up -d --build
```

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

```powershell

```

Каталог `data` подключается к контейнеру как постоянный локальный том.

## Тестирование

```powershell
python -m pytest -q
```

Офлайн-тесты не обращаются к ProxyAPI и проверяют:

- прежний endpoint `/triage` и его fallback;
- новый endpoint `/agent/chat`;
- валидацию входных и структурированных выходных данных;
- разделение checkpoint ID разных клиентов и диалогов;
- восстановление состояния из SQLite после нового подключения;
- сбор текста обращения без выдуманных полей;
- передачу данных из собственного tool в существующий триаж;
- SQLite и Turso без реальных сетевых запросов;
- ограничение частоты запросов.

## Ограничения учебной версии

- ответы модели и предварительная классификация требуют проверки человеком;
- `confidence` не является гарантией правильности;
- агент не ставит диагноз и не сообщает неподтверждённые цены или сроки;
- в демонстрации нельзя использовать реальные персональные данные;
- отправка сообщений клиенту и другие внешние действия не выполняются;
- долговременный профиль пользователя пока не реализован: сохраняется состояние
  конкретного диалога.

## Статус

Проект собран и проверен локально в Docker. Проходит 26 автоматических тестов.
Живой диалог через ProxyAPI подтвердил сбор обращения и вызов собственного tool.
Отдельный сценарий подтвердил восстановление SQLite-памяти после перезапуска
контейнера и изоляцию одинакового `thread_id` у разных клиентов.
