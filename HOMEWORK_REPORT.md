# Память в LangChain и других фреймворках

## Выбранные фреймворки

Для своих задач я выбрал LangChain вместе с LangGraph, LlamaIndex и Haystack.
Все три инструмента помогают создавать приложения на базе языковых моделей, но
решают эту задачу с разными акцентами.

### LangChain и LangGraph

LangChain даёт готовые компоненты для подключения моделей, инструментов,
структурированного ответа и памяти. LangGraph отвечает за управляемое состояние
процесса: можно хранить историю отдельного диалога, сохранять промежуточные шаги
и продолжать работу с нужного места.

Этот вариант лучше всего подходит моим Telegram-ботам, API и сервисам, где агент
должен не просто ответить один раз, а вести диалог, уточнять данные и вызывать
Python-функции. Например, помощник автосервиса может постепенно собрать сведения
об автомобиле и неисправности, а затем передать готовое обращение в обработку.

### LlamaIndex

LlamaIndex в первую очередь удобен для подключения внешних данных: документов,
баз знаний, файлов и векторных хранилищ. Он помогает загрузить данные, разбить их
на части, построить индекс и находить контекст для ответа модели.

В моих проектах LlamaIndex мог бы пригодиться для помощника по документации или
портфолио. Пользователь задаёт вопрос, система находит подходящие фрагменты в
README, отчётах или описаниях проектов и формирует ответ на их основе. Это ближе
к RAG и работе с базой знаний, чем к обычному хранению истории диалога.

### Haystack

Haystack ориентирован на управляемые поисковые и RAG-пайплайны. В нём можно
отдельно настраивать поиск документов, фильтрацию, генерацию ответа, состояние и
инструменты агента. Такой подход полезен, когда особенно важны понятная схема
обработки и контроль каждого этапа.

Мне Haystack может пригодиться для более крупной поисковой системы по документам
или обращениям клиентов. Для текущего небольшого проекта он был бы избыточен,
поэтому практическую часть я решил выполнить на LangChain и LangGraph.

## Вывод по сравнению

Для диалоговых агентов и автоматизации моих текущих Python-проектов удобнее
LangChain и LangGraph. LlamaIndex я бы выбрал для приложения, основной задачей
которого является поиск по собственным документам. Haystack подходит для более
строгого и масштабируемого поискового пайплайна, где нужно явно контролировать
его компоненты.

Главное, что я понял: память не находится внутри языковой модели. Приложение само
решает, какие сообщения и факты сохранить, как отделить пользователей и какую
часть сохранённого контекста передать модели при следующем запросе.

## Дополнительное задание

В качестве практической части я развил свой предыдущий проект Auto Service AI
Triage. Исходный сервис принимал уже готовый текст обращения, классифицировал его
и сохранял результат. Новая версия получила диалогового агента, который сначала
собирает недостающие сведения, а затем передаёт заполненную заявку в существующий
триаж.

Агент уточняет:

- автомобиль;
- описание проблемы;
- когда и при каких обстоятельствах она появилась;
- дополнительные важные сведения, если клиент их сообщил.

История каждого разговора сохраняется через SQLite-checkpoint LangGraph.
Сочетание `client_id` и `thread_id` преобразуется в отдельный идентификатор, поэтому
разговоры разных клиентов и разные темы одного клиента не должны смешиваться.

Я добавил собственный tool `submit_triage_request`. Модель видит только параметры,
которые нужно получить из разговора. Идентификатор клиента, настройки базы и ключ
API в параметры инструмента не передаются. После вызова tool обращение проходит
через прежнюю логику триажа, сохраняется в журнале, а агент получает номер заявки
и структурированный результат.

Ответ агента также имеет фиксированную структуру: сообщение клиенту, состояние
`collecting`, `submitted` или `error`, список недостающих сведений, номер заявки и
результат триажа. Это позволяет использовать ответ в API без ручного разбора
свободного текста модели.

## Проверка

Автоматическая проверка содержит 26 тестов. Они подтверждают работу прежнего
endpoint, нового контракта агента, изоляцию идентификаторов памяти, восстановление
checkpoint из SQLite, сбор текста обращения и передачу данных из собственного
tool в существующий триаж.

Дополнительно я собрал Docker-образ и провёл живой диалог через ProxyAPI. В первом
сообщении клиент указал автомобиль Lada Vesta и стук при повороте. Агент не
потерял эти сведения, уточнил время появления, а после сбора данных создал заявку
с категорией `support` и вернул её номер в структурированном ответе.

Отдельно проверил постоянство памяти: начал разговор о Kia Rio, перезапустил
контейнер и продолжил тот же `thread_id`. Агент восстановил автомобиль, симптом
и свой предыдущий вопрос из SQLite. Затем я отправил сообщение с тем же
`thread_id`, но другим `client_id`: агент не увидел чужой контекст и снова
запросил автомобиль. Значит, память сохраняется после перезапуска и изолирована
между клиентами.

Во время живой проверки обнаружился полезный крайний случай: после успешного
вызова tool агент мог продолжить лишние циклы генерации. Я сделал tool конечным
шагом и формирую итоговый ответ из фактически сохранённого результата. После
исправления все 26 тестов и повторный живой сценарий прошли успешно.
